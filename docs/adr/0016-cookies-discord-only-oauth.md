# Cookie sessions + Discord-only OAuth in v1.0

Auth uses a server-side `sessions` table `(id, user_id, created_at, last_seen_at, expires_at, ip, ua)` with an opaque token in `glyphoxa_session=<random>; HttpOnly; Secure; SameSite=Lax`. CSRF is double-submit (`X-CSRF-Token` header) for state-changing Connect calls.

OAuth in v1.0 is **Discord-only** — every GM is a Discord User by construction (per ADR-0003), and Google/GitHub raise account-linking complexity for no v1.0 win. Login screen shows Google/GitHub slots disabled with a "coming soon" hint; wired for real in v1.5+.

API keys are bearer-only (`Authorization: Bearer glx_<random>`) for service accounts (CI, scripts), schema `api_keys (id, tenant_id, user_id, name, hash, last_four, scopes, created_at, last_used_at, expires_at)`. The API-key field is **dropped from the human login page** — service-account keys and human session cookies should age and revoke differently.

Tenant scoping uses an `X-Tenant-Id` header on every Connect call, validated server-side against `tenant_members.user_id`. Tenant switching is a DOM update, not a session rotation; two browser tabs can hold two tenants simultaneously.

**Why JWT is rejected:** revocation pain, XSS attack surface, refresh-token dance complexity. Server-side sessions revoke instantly with a row delete.

## Amendment: session hygiene and proxy trust (2026-11-20, #643, #662)

Four refinements to the session mechanics above. The decision — server-side sessions, an opaque cookie token, double-submit CSRF — is unchanged.

- **The row stores a digest; the column keeps its name.** Since #636 `sessions.token` holds the SHA-256 (base64url) of the cookie secret, never the secret. Migration 00056 deletes expired rows and documents that with a column comment. Renaming the column to `token_hash` (as #643 proposed) was deliberately rejected: it would make the release non-rollbackable — an older binary fails every authenticated request against the renamed column — for a cosmetic gain. No rewrite step either: a plaintext row can only predate #636 (2026-09-02), sessions live 30 days, so those rows have expired — and a plaintext and a digest value are indistinguishable (both 43 base64url characters), so they could not be rehashed in place anyway. Any plaintext row that survives (a deployment upgrading straight from a pre-#636 build) is inert, because every lookup hashes the presented cookie first.
- **Expired rows are purged.** `Store.PurgeExpiredSessions` deletes rows a day past expiry, at every `web`/`all` boot and daily thereafter. Each row carries the login's IP and user agent; nothing removed them before.
- **`last_seen_at` is coarse.** `AuthenticateSession` refreshes it only once it is more than 5 minutes stale, so an authenticated request is a read, not a row rewrite. It is an audit column and takes no part in validation.
- **Proxy-supplied facts are not taken from the client.** Cookie `Secure` is derived once at boot from the scheme of `DISCORD_OAUTH_REDIRECT_URL` — the public URL the operator configured — instead of each request's `X-Forwarded-Proto`, which a client can set or omit and which silently downgraded the session cookie when a proxy did not send it. The session audit IP comes from the header the operator names in `GLYPHOXA_TRUSTED_CLIENT_IP_HEADER` (`CF-Connecting-IP` for a deployment reachable only through Cloudflare, which sets it), else the *last* `X-Forwarded-For` hop (the one the nearest proxy appended), else the socket peer; it used to be the first `X-Forwarded-For` hop, which is whatever the client typed. Which header to believe is configuration, never guessed: an unconfigured instance ignores a client-sent `CF-Connecting-IP` like any other forgeable header. Both are a required constructor argument of the auth handlers (`auth.EdgeConfig`), so neither can be forgotten at the composition root. Both rest on the ADR-0039 topology: the web tier is reached only through the deployment's reverse proxy.
