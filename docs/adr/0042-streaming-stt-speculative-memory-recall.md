# Streaming STT (Scribe v2 Realtime, manual commit) + speculative memory recall

Deciding how NPC memory retrieval (#122) threads into the latency-sensitive turn path surfaced the real bottleneck: the batch STT POST (`stt.Recognizer.Transcribe`, one `/v1/speech-to-text` call per endpointed utterance) is the ~1.5s that dominates the ~1.7s p95 response latency, and it leaves no text to speculate on until `STTFinal`. We pull **streaming STT into scope** rather than optimizing around it.

## What this decides

- **Provider: ElevenLabs Scribe v2 Realtime**, as a websocket sibling of the existing `scribe_v2` batch adapter. Stays inside the ADR-0039 MVP provider matrix and reuses the saved ElevenLabs BYOK key. Deepgram (named for STT in ADR-0004) stays a possible later addition behind the same interface; the batch adapter remains as fallback.
- **Local VAD stays the endpointing authority; the stream uses `commit_strategy: "manual"`.** Voiced audio (VAD-gated, with pre-roll) streams over a persistent per-Voice-Session websocket; `partial_transcript` messages flow during speech; the local VAD endpoint (incl. the #91 silence-clock) sends the manual commit, and `committed_transcript` becomes `STTFinal`. Provider-side VAD endpointing was rejected: barge-in's Confirm Window (ADR-0027) needs a local, network-independent VAD anyway, and two competing VADs create turn-boundary disagreement bugs; VAD-gating also keeps streamed-audio cost near batch parity. (This is the same division of labor Pipecat uses with this API.)
- **New `STTPartial` event** in the `voiceevent` taxonomy (ADR-0020): the mutable interim text of the in-progress utterance. Consumers must treat it as replaceable; only `STTFinal` reaches Address Detection and the Transcript.
- **Turn semantics are untouched.** Barge-in, Soft-overlap, Ensemble Turns, and deliver-then-commit (ADR-0012/0026/0027) key off local VAD and `STTFinal` exactly as today. What is rebuilt is the transcription transport: the serial POST worker becomes a stream manager with keepalive, bounded reconnect, and automatic fallback to the batch adapter when the stream is down.
- **NPC memory recall (#122) is speculative over partials, with a bounded-sync fallback.** During speech, stabilized partials are embedded and ANN retrieval (per ADR-0011's two modes) runs ahead of the turn; at `STTFinal`, if the final text matches the speculated query (normalized comparison), the prefetched chunks inject into the Hot Context memory slot at zero added latency; on mismatch — or whenever no partials are available (batch fallback, stream down, feature unconfigured) — retrieval runs inline under a hard budget (~250ms inside the turn ctx) and degrades to no-memory on timeout, with a Prometheus counter for skips and speculation misses.

## Expected effect

Endpoint→final drops from one full batch POST (~1.5s) to a manual-commit finalization (~100–300ms); response latency should fall from ~1.7s toward ~0.5s + LLM TTFT, and memory recall rides along at effectively zero marginal latency in the speculative path.

## Considered options

- **Bounded-sync retrieval only, keep batch STT** — rejected by the operator: it optimizes around the actual bottleneck. Kept as the fallback path, so the recall feature works with any batch-only STT provider.
- **Prefetch retrieval keyed on the previous turn** — rejected: the query vector misses the current utterance, which carries the retrieval key ("do you remember the ruby dagger?").
- **Provider-side VAD endpointing** — rejected, see above.
- **Deepgram as the streaming provider** — deferred: adds a second provider relationship (BYOK key, config UI, health) for maturity we don't yet know we need.

## Relationship to other ADRs

- **ADR-0011** — retrieval modes (NPC-knowledge vs world context) and async embeddings are consumed unchanged; this ADR only decides *when* retrieval runs.
- **ADR-0019/0026/0027** — endpointing authority, bus wiring, and barge-in semantics are deliberately preserved.
- **ADR-0020** — taxonomy gains `STTPartial`.
- **ADR-0021** — the websocket adapter needs a deterministic fake/replay harness like the batch cassettes before it gates CI.
- **ADR-0039** — MVP provider matrix unchanged (still Groq + ElevenLabs).

## Amendment 2026-11-20 — the batch fallback never fit its budget

A live production check (batch STT, the default) found memory recall degrading to no-memory on **every** turn (`glyphoxa_voice_memory_recall_total{outcome="skip"}` = 100%). Two causes, neither visible in tests with a fake embedder:

- **The inline fallback cannot finish in 250ms on the production node.** One spoken sentence takes the CPU-only Ollama instance ~340ms to embed, warm. The "kept as the fallback path" promise above was therefore false wherever streaming STT is off.
- **A cold model never loads.** Ollama unloads an idle model after five minutes; a recall that gives up at its budget makes Ollama abort the load, so recall calls alone never bring the model back.

Decisions:

- **The final's embed starts when `STTFinal` is published, under the recaller's own context**, not inside `Recall`. The recaller subscribes to `STTFinal` and embeds-and-prefetches unconditionally (no rate limit, no minimum length — a turn is about to ask for exactly this text), each final on its own bounded goroutine so table chatter never queues ahead of an addressed utterance. `Recall` joins that call instead of embedding the same text a second time behind it. This buys no head start — Address Detection is a synchronous text match, so `Recall` follows the final within microseconds — what it buys is that a turn running out of budget no longer cancels the request, so a cold model finishes loading.
- **The budget is 500ms by default** (`GLYPHOXA_RECALL_BUDGET`). It is a ceiling: a speculation hit over partials still costs a millisecond or two. On batch STT a turn that recalls now **pays the real embed time (~350ms on the production node) before its first LLM call.** We accept that in exchange for NPCs that remember; streaming STT remains the way to get recall at no added latency (it has been the default since the 2026-11-22 amendment below). A joined final counts as a `miss` in `glyphoxa_voice_memory_recall_total`, so `hit` keeps meaning "speculated over partials, free".
- **Speculation state is per campaign** (one cache slot and one in-flight final each, entries expire after two minutes), so concurrent sessions in one process neither serve nor evict each other's prefetch.
- **The embeddings model is pinned and pre-loaded**: every embed request carries `keep_alive: -1`, and the recaller warms the model at boot, retrying while the embeddings server is still coming up.

## Amendment 2026-11-22 — streaming is the default, and it stays streaming (#702)

Streaming shipped dark behind `GLYPHOXA_STT_STREAMING` and was soak-tested with closely spaced probe clips (#700). Live probes against the provider on 2026-11-22 showed why that soak looked better than a real table would have, and corrected two numbers this ADR opens with.

**Measured, not assumed.** Batch STT's speech-end → routed is 430–650 ms and streaming's is 150–290 ms (#700); a streamed commit round-trips in ~150–180 ms. The gain is therefore about 350 ms per turn — real, but not the "~1.5 s" bottleneck and "~1.7 s → ~0.5 s" effect claimed above, which were never reproduced. Partials arrive about once a second, the first about 2.3 s into the audio.

Decisions:

- **Streaming STT is on by default.** `GLYPHOXA_STT_STREAMING` is now the off-switch: only `0`/`false`/`no`/`off` (any case, trimmed) selects batch STT; unset, blank or anything else streams. It is read once at process start. To turn streaming off, set it to `0` on the pod that runs voice — `web.extraEnv` when web runs `-mode all`, `voice.extraEnv` in a split deployment — and restart the pod. The batch adapter stays the automatic per-utterance fallback either way, and `wirenpc.Config.STTStreaming` keeps a zero value of off, so tests, cassettes and benches that build a Config stay on batch.
- **The 15 s idle rule, and the keepalive that answers it.** The provider closes a realtime session 15 s after the last client *text* message, with a bare close 1000 and no error frame. Websocket pings do not count (pongs came back and the session still closed at 15.0 s), nor does `keepalive_interval_ms`; the window is not configurable. Because idle frames are never streamed (silence is not billed), every speaker who paused for 15 s lost their session, and the next utterance — the one that discovered the death — went to batch. The adapter's write pump now sends an **empty `input_audio_chunk`** (no audio, `commit: false`) once 5 s pass without a client text message. Live, that held a session across a 20 s gap between two real clips, both committing on the same session (149 ms and 177 ms); the control run without it closed at ~15.4 s. An empty chunk bills nothing and adds nothing to the next commit. The websocket ping stays, for dead-peer detection only. If the provider ever stops honouring empty chunks, 100 ms of silence every 5 s is the documented-safe alternative (~2 % billed duty).
- **The adapter reports a session's death when it happens.** `stt.StreamConfig.OnClosed(err)` fires exactly once for any end of a session. The stream manager drops the session and redials immediately when it had been healthy (up ≥ 10 s), so the redial completes during the speaker's silence rather than costing an utterance. A session that dies younger than that — a provider that accepts the dial and drops it — is redialed after the bounded backoff, which grows as before; auth-class causes still wait at the cap. The backoff is forgiven by a session that proved healthy (lived ≥ 10 s, or resolved a commit), so a clean idle close can no longer ratchet it 1 → 2 → 4 → … → 30 s, which is what had been turning streaming off in practice for sparse speakers. Age forgives only a session that *ended* — the provider or the network closed it. A session the manager itself retires, because a commit failed or was never answered, has just shown it does not work however long it sat there: its redial waits the growing backoff at any age, and only a resolved commit resets it. Otherwise a provider that accepts the handshake and answers no commit would cost every turn the full 3 s commit timeout for as long as the incident lasts; with the backoff, turns in between go straight to batch. A session that dies under an open utterance sends that utterance to batch even if the redial wins the race against the next frame; it never continues on the fresh session.
- **`commit_throttled` is fatal, and any commit error retires the session.** The frame was modelled as "this commit failed, the session lives". Live it reads `Session closed: only 0.00s of uncommitted audio. You need at least 0.3s of uncommitted audio before committing.` and the provider closes the socket after it (reachable when an utterance streams under 0.3 s). The adapter now treats it as fatal. Independently, the manager retires the issuing session on *every* commit that resolves with an error, as it already did on a commit timeout (#639): the utterance's audio is still at the provider, uncommitted, and on a surviving session it would be transcribed as the start of the next utterance.
- **The final preempts speculation over partials** (the #700 blocker: `memory speculation: embed failed`, and recalls skipped behind the embeddings queue). One embeddings slot serves the speculator, the finals and the inline miss in turn; at speech end the previous partial's embed was still running, the newest partial waited in the mailbox, and the final queued behind both — then the stale partial was embedded *after* the final. Now a final (a) drops its session's pending partial, (b) if the in-flight speculative embed is for the same normalized text and campaign, registers it as the campaign's flight so `Recall` joins it — no second embed — and (c) otherwise cancels it, without a warning log (a preempted embed is not a failure). In addition, **only partials whose raw text ends in sentence punctuation (`.` `?` `!` `…`) are speculated**: partials are growing prefixes, and only one that already closes a sentence can equal the final. A debounce was considered and rejected — partials arrive a second apart, so a short one changes nothing and a long one cannot fire before the final.
- **A missing API key is an auth-class dial failure** (it waits at the backoff cap instead of redialing a dial that cannot succeed), and the manager now logs: the first failed dial of a run and any change of error code, the reconnect that ends the run, and the unexpected end of a live session. Before, a keyless deployment redialed every 30 s forever without a line.
- **Streamed and fallback finals are counted apart.** `glyphoxa_voice_stt_final_total{provider,transport,reason}`: `stream`/`committed`; `batch_fallback`/`stream_down` (no session at speech start), `stream_died`, `commit_error`, `commit_timeout`; `batch`/`streaming_off`, `lane_cap`. Nothing else distinguishes them — the latency histogram and the provider counters record both identically — so this is the series a soak is judged by.
- **The default (unattributed) lane dials on its first speech**, not at bind. Inbound frames are speaker-stamped, so this lane normally never speaks; eagerly dialed it used to idle out after 15 s, but kept alive it would hold a realtime connection for the whole Voice Session.

Consequences and what is still open:

- Live connections now equal the Speaker Lanes active in the last two minutes (capped by `GLYPHOXA_STT_STREAM_MAX_LANES`, default 4, per Voice Session) — not the concurrent speakers ADR-0050 originally sized for; ADR-0050 carries the matching amendment. The plan's realtime concurrency and session time limits are unverified and need the soak.
- An utterance shorter than about 3 s gets no partial that closes a sentence, so it pays the final's embed inside the recall budget; keep `GLYPHOXA_RECALL_BUDGET` at 800 ms on a CPU-only embeddings node.
- Not done here, in order of expected value: replaying a lane's buffered audio when its first dial completes mid-utterance (a freshly created lane's first utterance is batch today); committing proactively at 25–30 s so the provider's own auto-commit cannot split a long utterance; per-speaker speculation state (the mailbox is one slot per process). (Biasing recognition with `keyterms` / `language_code` was done the same day — next amendment.)

## Amendment 2026-11-22 — the names at the table are sent to the recognizer as keyterms (#701)

Address Detection matches names in the STT final (ADR-0024), and since the 2026-11-20 amendment there a name shorter than four runes is exact-only. That stopped "Bart" answering "Start"; it also meant a three-letter name the recognizer misheard was simply not heard ("Flo, woran erinnerst du dich" arrived as "So, woran…", "Flo, stop." as "Flow, stopp." — #701). The recognizer had never been told which names to expect.

**Measured** (live probe 2026-11-22, TTS-generated German clips, three voices, Scribe v2 batch and Scribe v2 Realtime):

- Both endpoints take `keyterms`: a repeated multipart field on batch, a repeated query parameter on realtime (echoed in `session_started.config.keyterms`).
- Exact-name hits on clean audio rose from 56 % to 100 % on batch and from 41 % to 100 % on realtime. A lone "Flo?" routed in 2 of 21 runs without keyterms and 21 of 21 with them. Through the shipped adapter (`TestLive_Keyterms_BothTransports`, n = 3 per cell, list `Flo, Glyphoxa`): "Flo?" went from "Flow?"/"Flow." to "Flo?"/"Flo." and "Flo, stopp." from "Flou, stopp!"/"Vloer, stop." to "Flo, stop!"/"Flo, stop." on both transports, 3 of 3 each.
- **A one-term list is weaker on realtime.** With `Flo` as the only keyterm the lone "Flo?" was heard 2 times in 9 on realtime (9 in 9 on batch); with a two-term and with a nine-term list it was 6 in 6. A Campaign's list always carries the Butler beside the Cast, so a real session never sends one term, but this is one clip, a handful of runs, and unexplained.
- No measurable latency change: realtime commit → final stayed ~160 ms.
- **The realtime limits are hard.** A 51st term, or more than 1000 characters in total, is answered with an `invalid_request` frame *instead of* `session_started`, and the session never starts; exactly 50 terms is accepted. Batch documents 1000 terms, 50 characters and 5 words per term, forbids `< > { } [ ] \`, and bills a 20 s minimum per request past 100 terms.
- **Boundary probe** (2026-11-22, 28 lists against each endpoint; realtime with no audio sent, batch with one 0.65 s clip). *Realtime:* the total is counted in characters, not bytes — exactly 1000 starts a session (20 × 50, 25 × 40, 50 × 20, and 25 terms of 40 two-byte runes = 2000 bytes), 1001 is refused with "Total length of keyterms cannot exceed 1000 characters. You provided 1001 characters."; there is no per-term limit (a 51-character term and a 6-word term start a session). *Batch:* the per-term limits are enforced with HTTP 400 `validation_error` (`invalid_keyword_length` past 50 characters, counted in characters; `invalid_keyword_spaces` past 4 spaces — the "5 words" are counted by spaces, so hyphens, digits and apostrophes add none); it has no 1000-character total. *Both* accepted everything else tried: punctuation-only and zero-width-only terms, emoji, quotes, `/ & % + = # ?`, a comma inside a term, duplicates differing in case, punctuation, NFC/NFD or ß/SS, digits-only terms, and the sanitiser's own maximum (50 terms, 1000 bytes). So the sanitiser below is at least as strict as each endpoint on every limit found, and no input that passes it was refused.
- The configuration is fixed per connection; a different list needs a redial.
- **Harm.** Speech that sounds nothing like a name never gained one. A true homophone is rewritten to the keyterm: "Der Floh springt über den Tisch" → "Der Flo springt …", "Der Flow des Flusses" → "Der Flo des Flusses", a lone "Flow." → "Flo.". The rewritten word then routes as an exact name.
- **Cost.** +$0.05 per audio-hour on batch ($0.20 → $0.25), +$0.08 on realtime ($0.22 → $0.30).
- `previous_text` was tested as an alternative and rejected: it applies once per connection, its effect decays, and it leaks into the transcript as artefacts. `language_code` alone does nothing for names, but it stopped wrong-script output on very short utterances.

Decisions:

- **Keyterms are on by default, on both transports.** `GLYPHOXA_STT_KEYTERMS` is the off-switch (`0`/`false`/`no`/`off`). One transport would not do: with streaming on, an utterance still falls back to batch per utterance, and the same name must not be transcribed two ways depending on the path it took. `stt.StreamConfig.Terms` carries the list to a realtime session; the batch client takes it as a construction option (`elevenlabs.WithTerms`) because one client is built per Voice Session and the list is fixed for it — no optional per-call interface that a wrapper could hide. A test drives the production wiring against a fake of both endpoints and checks every realtime dial (default lane and Speaker Lane) and every batch request, the batch fallback included.
- **The list is built once per Voice Session, by priority:** first the names that route — every Cast NPC's, then the Butler's — then those NPCs' aliases in the same order (the names Address Detection matches, not the derived truncation aliases), then the player characters' names, then their aliases. Names come before any alias so that at the 50-term cap a big Cast loses spellings, not an NPC late in the roster or the Butler. A roster edit applies to the next session, like the roster itself. Session start logs the count, never the names, at info level.
- **One sanitiser for both paths, sized to the stricter endpoint:** trim, strip the forbidden characters, cut each term to 5 words and 50 characters, drop a term with no letter or digit left, de-duplicate ignoring case, then end the list before the 51st term or the 1001st character (counted in bytes, which can only be stricter). Low priority is what gets cut.
- **A refused list fails open.** The list is tenant free text and the sanitiser is the only thing in front of it, so a refusal must not cost the session its hearing. *Batch:* a 400/422 answer to a request that carried keyterms is retried at once without them; if that succeeds the list was the reason, the utterance is transcribed unbiased instead of lost, and the client sends no keyterms again (if the retry is refused too, the list was not the reason and stays). *Realtime:* `invalid_request` in place of `session_started` on a session that carried keyterms ends it with `stt.CodeTermsRefused` and latches the same client, so the redial — on the ordinary backoff, not the cap — and the batch path both go out without keyterms. The latch lives in the adapter client, one per connection cycle of a Voice Session: a reconnect offers the list once more. One warning on the session's logger (`stt keyterms: the provider refused the keyterm list`), with the count and without the names; the provider's detail text, which may quote a term, only at debug. An `invalid_request` the adapter cannot attribute to keyterms (none were sent, or the session had started) stays fatal and waits at the backoff cap as before.
- **The homophone risk is accepted, with three mitigations.** (1) A name that is an everyday word of the Campaign Language, per Address Detection's own list (`address.IsCommonWord`), is not sent: an NPC called "Wolf" must not turn every spoken "Wolf" into a route. That list was built for the fuzzy tiers and is incomplete below four runes — English has none there, German a dozen function words (`mal`, `weg`, `von`, …) — so most short names that are themselves words are still sent, and a German NPC called "Mal" or "Weg" is not. (2) The exact-only floor for names under four runes is **not** loosened — keyterms fix the transcript, the matcher stays as strict as before. (3) The off-switch, and a live checklist item for the homophone negatives (`docs/devs/voice-tests.md`). What remains: a table that really says "Floh" or "Flow" while an NPC is called Flo will address him. That was already true of any exact name used as a noun (ADR-0024, "Der Bart muss ab."); keyterms widen it from the name's spelling to its homophones.
- **The language hint is opt-in.** `GLYPHOXA_STT_LANGUAGE_HINT` sends the Campaign Language as `language_code` on both transports; the default stays auto-detect, because tables mix languages.
- **The spend meter prices STT at $0.30 per audio-hour**, the dearest thing the binary now sends (realtime with keyterms), replacing a stale $0.40. The usage capture point knows neither the transport nor whether keyterms were sent, so the estimate is an upper bound for all four combinations.

Not done here: Knowledge Graph entity names as terms (places and items are said as often as names, but the list is capped at 50 and they do not route); a vocative-position rule for short names, which would take the homophone residue out of the matcher instead of the recognizer; a hint in the Cast editor when a name is short or is an everyday word; and `scribe_v3_live`.
